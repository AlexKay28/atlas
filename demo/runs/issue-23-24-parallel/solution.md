## Issue #23 — Branch workspaces, resource claims, explicit artifact merge

**Branch workspaces.** A branch is a PAR branch (`par<k>`) or a scatter candidate (`cand<k>`). When a dispatch inside a branch runs an effectful command — decided by the registry contract lookup already central in the coordinator (`_effectful_commands()`: durable-write effect classes, i.e. `edit` and `remember` in the builtin registry) — the injected `_workspace_root` becomes the branch's isolated subdirectory `<base>/branches/<branch_id>/`, nesting under the enclosing branch's own directory for blocks inside branch runs. Read-only dispatches are never re-rooted (only effectful commands receive `_workspace_root` at all), so reads keep seeing the main workspace. Top-level dispatches are byte-identical to before (asserted by tests).

**Resource claims (`src/tikhon/claims.py`, new).** `ResourceLedger.claim(resource, owner) -> bool` / `release(resource, owner) -> bool` / `holder(resource)`: exclusive in-process holds, one lock over a dict, strict re-claim rejection (a hold is a hold; the holder must release first). The coordinator mints one run-scoped ledger per `execute()` call and threads it through the whole execution tree like the #22 budget gate. Wiring without new syntax: an effectful dispatch inside a branch claims `workspace:<branch identity>` for exactly the handler's duration (released in `finally`), and the artifact merge claims `merge:<run_id>` for its duration — so merges serialize by contract. Claim resources embed the run-scoped branch identity (`workspace:<run_id>:par<k>`, `workspace:<run_id>:inv-K.cand<k>`) because bare `par<k>`/`cand<k>` ids are ambiguous across multiple blocks; contention therefore cannot arise within a block, and the ledger primitive's serialization property is proven directly by a cross-thread test. DISPATCHED payloads are annotated with `"resource_claims": [...]` only when a claim is actually held — no new event types, and non-branch event streams stay byte-identical.

**Explicit artifact merge.** After a join (scatter gather; PAR barrier), a deterministic merge step collects the branches' produced `ART.*` nodes (an ART node's string value is a workspace-relative path inside its branch workspace), holds `merge:<run_id>`, checks cross-branch collisions in branch-then-target order, copies each found artifact file to the same relative path under the parent workspace root, and records the accounting — every adopted artifact path, its branch, and whether its file was integrated — in the join's own commit (the gather SUCCEEDED payload's `"merge"` block; per-branch CHILD_ADOPTED payloads plus the PAR_JOINED payload for PAR). The same relative path produced by two different branches is an explicit conflict: the run fails atomically with an error naming the path and both branches — no silent overwrite, no last-writer-wins, and nothing after the barrier executes. The merge is workspace-gated for scatter (pre-#23 programs without a declared workspace are untouched) and releases its claim on every path.

## Issue #24 — PAR blocks with an explicit barrier

**Grammar.** `PAR MAX <n>` on its own line, followed by two or more indented branch lines — each a full `step.<id>: DO ... -> targets` invocation line or a `CALL protocol.name(...) -> targets` line — terminated by a matching-dedent `BARRIER` line that optionally declares targets (`BARRIER -> t1, t2`). Branch ids are deterministic (`par<k>`, 1-based source order) and positional, so they are not part of the canonical seal. Validation: sibling-output reads before the join are rejected (branch lines validate against the pre-PAR namespace; branch targets join `available` only after the barrier), duplicate parent output targets fail (across branches and against existing parent nodes), a declared BARRIER list must equal the union of the branches' targets exactly, branch REVISE/RETIRE is rejected (corrections address parent-namespace nodes; branch state is isolated), and empty/single-branch blocks are parse errors. Programs without PAR seal byte-identically to before.

**Runtime.** The PAR block (branches + barrier) is one plan entry. Branches dispatch concurrently onto a pool capped at `min(MAX, branch count)`, further capped tree-wide by the budget's shared semaphore; the entry checks the budget's global deadline and child-depth cap before dispatching. Every branch executes as an isolated child-scoped run `<run_id>:par<k>` — a CALL branch reuses the CALL child-run machinery; a DO branch executes a synthetic single-invocation child program whose INPUT declarations carry its dispatch-resolved arguments — so state isolation comes for free from the #20 child-run machinery, and #23's workspace isolation and claims are active inside every branch. All parent-side commits happen on the coordinator's single-writer thread (pool threads drive child runs only, exactly like the #21 frontier).

**Barrier + adoption.** The barrier blocks until every branch is terminal (proven by a test where the fast branch's output is not adoptable while the slow branch holds the barrier open). All succeeded: one CHILD_ADOPTED per branch (adopted map + artifact accounting) with the branch's ledger task settled atomically at its completion, then the explicit artifact merge, then one PAR_JOINED event recording branch statuses, declared targets and merged artifacts, and a single entry-terminal SUCCEEDED committing all adopted targets in branch order — the atomically published declared outputs. One ledger task per branch (`PAR branch <k>: <summary>`), no block task; branch tasks stay PENDING while their child runs execute (the strict single-IN_PROGRESS invariant holds) and start+complete in one batch at settlement. Any branch failure: one FAILED event, the failed branch's task settled-and-cancelled, every unsettled sibling task cancelled, in-flight pool work drained and its results discarded uncommitted (never adopted), RUN_FINISHED failed — one atomic batch, audit-clean. Nested PAR is expressed by a CALL branch whose protocol contains its own PAR block and is bounded by the budget's colon-count child-depth cap (default depth 8 succeeds; `max_child_depth=1` fails the inner branches and the run atomically).

**Determinism/replay/resume.** Branch event order may interleave by completion order; the terminal delta order, final projection, and state version are completion-order-independent (permutation test), and replay after reopening the store is identical (event-for-event and projection-equal). Resume: PAR entries carry no block task, so `_resume_existing_run` aligns ledger tasks with the plan's non-PAR positions ("static positions"), accepts `PAR branch <k>: ...` texts as ledger extras, excludes `par<k>` ids from the positional success set, and re-drives a crashed PAR entry by skipping branches whose tasks already completed (re-reading their committed child state) — a crash after the PAR entry commits resumes cleanly to a succeeded run (verified). Mid-PAR crash resume works through the same path with one caveat recorded below.

**Audit.** The only audit.py change is the anticipated false-positive fix: a PAR barrier's entry-terminal SUCCEEDED (and a join-level PAR failure's FAILED) carry no task_id because a PAR block owns no ledger task of its own; these events are recognized by their `"par"` payload marker and exempted from the task_id requirement only (instruction_id still required). PAR_JOINED itself is not invocation-bound. Parent, CALL child, PAR branch and nested runs all audit clean in every new test.

## Deviations / limitations

1. **Resume gaps (documented, resume.py untouched per scope):** post-PAR-crash resume works (verified); a crash *mid*-PAR resumes by re-driving the entry — branches whose tasks already completed are skipped and their outputs re-read from committed child state, but branches re-driven from a pre-adoption crash window can re-emit their parent-side branch accounting events (RESULT_RECEIVED/CHILD_ADOPTED) a second time; the store's dup-SUCCEEDED guard and the entry-terminal delta keep state correct, and no existing invariant is violated, but the duplicated accounting is ugly. Budgets are not re-instated on resume (pre-existing #22 gap).
2. **Cancellation is cooperative:** on branch failure the drain waits for started child runs to reach their own terminal states (their results are discarded uncommitted); external effects of a cancelled branch are not rolled back (issue #23 explicitly does not promise this). Branch workspace files of cancelled branches remain as recorded evidence.
3. **Branch workspace dirs are reused across blocks** with the same shape (`branches/par1` of two sequential PAR blocks is the same directory; nested blocks nest under the enclosing branch dir, keeping trees disjoint). Merges only integrate each joining block's own declared ART paths, so leftovers are never integrated; concurrent blocks cannot exist (blocks execute sequentially).
4. **The merge integrates files leniently:** an ART node whose value is not a string (or whose file is absent from the branch workspace) is adopted as a node with `copied: false` accounting rather than failing the run; collision detection applies to string-valued ART paths across different branches of one join.
5. **BARRIER target declaration is pinned to the union** of branch targets (a subset/superset declaration is a validation error) — the explicit declaration documents and pins the adoption mapping rather than selecting a partial publish; partial publication would leave branch outputs dangling.
6. **A join-level PAR failure (merge collision) carries its FAILED event on the PAR entry's positional id with the `"par"` payload marker** instead of a branch attribution (blaming one branch would be false); the audit exempts exactly these marked, task-less events.
