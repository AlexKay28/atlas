## Issue #21 — Concurrent execution frontier (ready-task scheduling, single-writer commits)

**Scheduling.** `SequentialCoordinator.execute(..., max_workers: int = 1)` — with the default `1` the historical blocking sequential loop runs untouched. With `max_workers > 1` the plan is driven by `_drive_plan_concurrent`: a ready task is one whose dependency DAG ancestors are all terminal. The DAG (`_build_dependency_dag`) is computed from ref usage with three edge kinds — RAW (an entry depends on every earlier producer of a ref it consumes), WAW (on every earlier producer of a ref it writes) and WAR (a writer — including RETIRE/REVISE — depends on every earlier reader or writer of that ref). Read-read pairs carry no edge, so ref-disjoint steps overlap. Every entry therefore observes exactly the committed state its sequential execution would have seen, which is what makes the final state completion-order-independent. Ready entries dispatch in stable plan order up to `max_workers` onto a `ThreadPoolExecutor`; conditional DO entries and CALL entries serialize naturally behind the refs their conditions/arguments consume (documented in the method docstring).

**Single writer.** The pool executes worker handlers and CALL child runs only; every commit — task_started+READY batch, DISPATCHED, RESULT_RECEIVED, VALIDATION_PASSED, the atomic SUCCEEDED (`expected_state_version` CAS) batch, CHILD_ADOPTED, failure batches — happens on the coordinator thread through the existing `append_batch` path, so per-invocation event shapes are identical to the sequential loop. `EventStore` became thread-safe for the pool-thread child runs: one reentrant lock around every connection access and `check_same_thread=False` on the single SQLite connection; `BEGIN IMMEDIATE` batches (gapless seq) and CAS state versions are unchanged.

**Ledger relaxation.** The strict one-IN_PROGRESS invariant is deliberately relaxed for concurrent runs only: `TaskLedger(allow_concurrent=True)` skips the single-in-progress check in both `start_task` and the event application path (`_apply`), so replay reconstructs the same multi-IN_PROGRESS intermediate states. The flag rides on the run: the concurrent coordinator marks run metadata `concurrent: true` (+ `max_workers`), and `EventStore.task_ledger` auto-detects it — live batch validation and later replay both reconstruct correctly without touching any event payload. Default stays strict. Concurrent-run resume detects the same marker, replaces the sequential prefix invariant with a plan-range validation (a concurrent run's SUCCEEDED set is generally not a prefix), and re-drives the remaining entries through the frontier (in-flight steps re-execute at-least-once with the existing prior-lifecycle-event guards).

**Failure/cancellation.** A failing invocation commits the standard atomic failure batch (FAILED + invocation_recorded + task_cancelled + cancellation of every non-terminal task + RUN_FINISHED failed) and then drains the pool: not-started futures are cancelled, started handlers run to completion with their results discarded uncommitted — a late result can never overwrite an accepted output. `crash_hook` fires at the sequential site (before VALIDATION_PASSED) and propagates uncaught, preserving the true crash window.

## Issue #22 — Execution-tree budgets (global concurrency, deadlines, nested cancellation)

**`src/tikhon/budgets.py`** defines the frozen `ExecutionBudget(max_concurrent_workers=4, global_deadline_seconds=None, per_invocation_deadline_seconds=None, max_child_depth=8)` with strict validation, and `BudgetGate` — the per-`execute`-call live gate (shared `BoundedSemaphore`, monotonic run-start clock, colon-count child-depth rule) threaded through both drives and every CALL child as a `gate=None` keyword. A budget only caps, never enables: concurrency still requires `max_workers > 1`, and `budget=None` is byte-identical to no budget (asserted by comparing full event streams from two stores).

**Global concurrency.** Every handler execution tree-wide — parent frontier workers and child-run step executions alike — holds one slot from the single shared semaphore; the frontier pool size is independent, so the semaphore (not the pool) is what the cap tests observe. Waiting orchestration frames hold no slot: a parent CALL awaiting its child occupies nothing, so `max_concurrent_workers=1` cannot deadlock a parent-child pair (the child's steps acquire and release their own slots).

**Deadlines.** The global deadline is checked at the frontier loop top and before each sequential dispatch (which is also "before a child starts"); expiry with work remaining commits one atomic batch — in-flight invocations marked FAILED `"cancelled: global deadline exceeded"`, remaining tasks cancelled, `RUN_FINISHED` failed `"global deadline exceeded"` — and only then drains the pool (commit-before-drain, so the markers are never lost). Child runs share the gate and fail themselves at their own dispatch boundaries. Per-invocation deadlines are enforced in the frontier via `futures.wait` timeouts (an overrunning invocation fails through the standard atomic path with `"deadline exceeded"`; its late result is discarded) and in the sequential drive via a post-handler check (`BudgetDeadlineExceeded`), since a running handler cannot be interrupted.

**Nested cancellation + depth.** The depth cap is checked before a CALL dispatches (both drives): a child whose run id nests deeper than `max_child_depth` fails that CALL atomically and the grandchild run is never created. Cancelled children never adopt: the CALL's failure path runs before any adoption logic. `ModelWorker` gained an optional `deadline_seconds` that binds the execution budget's deadline into every rendered `TaskEnvelope` (`min` with the command contract's own `max_seconds`; `None` unchanged) — envelope.py itself untouched, the field already existed.

## Deviations / limitations

1. **Reservation accounting is not implemented** (issue #22's "reserve capacity … reconcile measured usage", token/cost allocation, retry races, reopen/resume budget re-anchoring): the practical scope here is the shared concurrency semaphore, deadlines, depth and cancellation. Budgets on resume are not re-instated (a resumed run continues without its original budget).
2. **Cancellation is cooperative**: a started handler cannot be interrupted — its result is discarded uncommitted, and the drain waits for it; a handler that never returns would stall the drain.
3. **Strict replay of a concurrent run's stream raises** at the multi-IN_PROGRESS window unless replayed with the flag (auto-detected through the store; `TaskLedger.from_events` direct callers must pass `allow_concurrent=True`) — the deliberate relaxation, documented on the ledger and asserted in tests.
4. **Fairness between branches** (issue #22's "one child cannot monopolize the tree") is not scheduled — the semaphore is not FIFO.
